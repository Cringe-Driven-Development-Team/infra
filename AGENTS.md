# Инструкции для агентов

Общепроектный контекст, действующая архитектура и планы развития проекта — в
[Контекст проекта](https://docs.cellestial.ru/project-context).
Спеки и планы реализации конкретной задачи размещай в репозитории, где выполняется
работа; общие для нескольких компонентов решения отражай в `docs`.
Перед правкой инфраструктуры читай `pulumi/` и `ansible/`; состояние стенда прямо сейчас
подтверждай соответствующими свидетельствами или проверкой стенда.

Устройство репозитория и локальные команды — в [README.md](README.md), порядок эксплуатации —
в [RUNBOOK.md](RUNBOOK.md). Подробности инструментов — в [Pulumi README](pulumi/README.md)
и [Ansible README](ansible/README.md). Задачи и PR веди по
[правилам команды](https://github.com/Cringe-Driven-Development-Team/.github/blob/main/CONTRIBUTING.md).

## Wiki и общее пространство

Для поиска контекста об устройстве infra начни с `openwiki_search`, затем прочитай
нужный раздел через `openwiki_read` с ID wiki из результата. Если ответа достаточно
и нет противоречий, остановись. При обычном чтении опубликованная wiki считается
актуальной; её актуальность обеспечивает процесс обновления и публикации.
Не проверяй свежесть, не сравнивай SHA и не делай `git fetch` или grep по исходникам
ради перепроверки ответа. Конкретный исходник нужен при пробеле, противоречии
или для внесения изменений; явные ошибки инструментов не игнорируй.
Wiki описывает декларативный код и не доказывает состояние Selectel прямо сейчас.
Общая архитектура и проверенный прод —
[wiki docs](https://github.com/Cringe-Driven-Development-Team/docs/tree/main/openwiki),
планы — модули docs. Не загружай wiki в начале каждой задачи;
для простой правки известного файла поиск по wiki не обязателен.

Определи корень текущего checkout командой `git rev-parse --show-toplevel` и
проверь `git remote get-url origin`: ожидается `Cringe-Driven-Development-Team/infra`.
Передавай этот абсолютный корень как `root` в `openwiki_search`. В связанном
workspace поиск охватывает соседние wiki; в `openwiki_read` передавай ID `wiki`
из результата. Не рассчитывай на сохранённые абсолютные пути.

Клоны `docs`, `frontend`, `backend`, `infra` держим рядом. Если работа идёт из
worktree, основной checkout находится через
`dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`; соседей ищи
относительно него и проверяй их `origin` в организации. Для общего поиска один
раз запусти `openwiki link` из родительской папки, выбери четыре готовые wiki и
назови пространство `CDD`. Реестр локальный, не коммить его. При нескольких
пространствах выбери активное `openwiki workspace use CDD`.

Проверки свежести (`bun scripts/openwiki-check.ts --against <SHA>` у владельца)
относятся к обслуживанию, генерации, CI и явной диагностике по запросу пользователя.
Без MCP читай `openwiki/quickstart.md` и нужную Markdown-страницу
с тем же правилом остановки при достаточном ответе;
если wiki ещё не создана, переходи к `SUMMARY.md`, `pulumi/` и `ansible/`.
Если соседнего клона нет, используй GitHub Markdown и предложи клонировать его
рядом. Реальное состояние облака и выкатки проверяй отдельно по стенду.

## Учебный проект: совместимость и прод

У проекта нет живых пользователей; преподаватели проверяют прод примерно раз в месяц.
Между проверками допустимы временная недоступность и несовместимость фронта и бэка
после выкладки одной стороны. Не добавляй по своей инициативе в задачи, планы,
приёмку или код поддержку старого API/клиента, legacy-режимы, поэтапное
переключение, безостановочный деплой и требования высокого uptime. Делай это
только по прямому требованию владельца для конкретной задачи.

Если фронт и бэк можно реализовать и проверить локально по согласованному
целевому контракту, работай над ними независимо. Временная поломка прода
между выкладками не создаёт связи `Blocked by`; проверь интеграцию после обеих
задач. К преподавательской проверке прод должен работать.
